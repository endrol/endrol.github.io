**Saturday** は、Claude Code の上に作ったハンズフリーの音声アシスタントだ。「Saturday」と呼んで、どのプロジェクトについてでも質問すると、4〜6 秒後に一文の答えが声で返ってくる。費用は 1 往復あたり約 $0.002。実際の変更は該当プロジェクトの中で起動した Claude Code セッションに渡り、危険な操作は画面上のキー入力を待つ。

設計ルールはひとつ。**音声レイヤーは考えない。** 音声認識と音声合成は、ただの耳と口だ。答えも、ファイルの読み込みも、編集も、すべて Claude Code から来る。この記事では、その配線、こうなった理由、そして途中で壊れたものを紹介する。

## 仕組み

:::message
アニメーション付きの構成図（各ボックスにホバーで説明）は元の記事にあります：https://endrol.github.io/posts/saturday-voice-claude-code/

| 部分 | 担当 | 補足 |
| --- | --- | --- |
| ウェイクワード | Whisper small（MLX）、Mac 上 | テストクリップ 14/14、約 190 ms。待機中は何もストリームせず、課金もゼロ。 |
| 耳 | `gpt-live-transcribe` | 話している間からストリーム。1 秒の間で文の終わりと判断し、話し終えてから約 1.6 秒でテキストが揃う。 |
| 頭脳 | `~/workspace` に常駐するウォームな Claude Code セッション（Agent SDK） | Sonnet、low effort、Claude のサブスクリプション枠。すべて読めるが、何も変更しない。 |
| 口 | `gpt-realtime-2.1-mini` | Claude の一文を一字一句そのまま読み上げる。1 回約 $0.002。 |
| ワーカー | 各プロジェクトの中の Claude Code セッション | 小さな変更は Sonnet、重い仕事は Opus。ツール `work_in` ひとつで起動する。 |

Claude が 2.5 秒経っても答えないときは、「Let me check.」のような短いつなぎを挟む。誰も話さず、動いているタスクもない状態が 10 秒続くと待機に戻る。

内部的には、Saturday はイベントを JSON 行として発行するコアと、それを描画するだけのフロントエンドに分かれている。ターミナル UI、`--headless` モード、記録したセッションを再生する `--replay`。毎回の実行は `~/.saturday/sessions/` に記録されるので、固まったときのデバッグはスクショを頼むのではなくリプレイで済む。

## なぜ音声レイヤーに考えさせないのか

最初のバージョンは **GPT-Live-1** を使っていた。推論を自分のバックエンドに委ねる全二重の音声モデルだ。自然には聞こえたが、問題が 2 つあった。

- 接続中は **1 分あたり $0.05**、無音の時間も含めて課金される。1 時間でおよそ $3。
- バックエンドの答えを**言い換える**。あるテストでは、詳しく聞かれたときに、Claude が一言も言っていない締め切り（「木曜までに…金曜までに…」）をでっち上げた。

事実を足してしまう音声レイヤーでは意味がない。そこで素直なカスケードに置き換えた。文字起こし、Claude に聞く、答えをそのまま読み上げる。テストでは、台本どおりの 4 つの答えが 4 つとも一字一句そのまま読まれ、ノート PC のスピーカー越しの 1 往復はエンドツーエンドで $0.0036 だった。GPT-Live はオプションの「ナチュラルモード」として数時間残ったが、約 25 回の実行で 1 回しか使われず、約 400 行のコードとともに削除された。

## 読むのはひとつの会話、書くのはワーカー

自分が話しかけるのは常にひとつの会話、`~/workspace` にいる頭脳だけだ。どのプロジェクトも読めて質問に答えられるが、何も編集できない。変更、副作用のあるコマンド、長い調査は `work_in` を通る。

```python
@tool(
    "work_in",
    "Hand work to Saturday's worker inside one of LUO's projects: a Claude Code session "
    "started in that project's folder, so its CLAUDE.md, permission rules and hooks "
    "apply. Use it for any change (editing or writing files, commands with side effects, "
    "commits) and for heavy work (deep investigation, debugging, design). Runs in the "
    "background and returns at once; the result comes back to you as a message.",
    ...
)
```

この分け方の理由は Claude Code の仕様にある。**セッションがプロジェクトの CLAUDE.md、`.claude/settings.json`、hooks を読み込むのは、起動したディレクトリからだけ。** `~/workspace` にいる頭脳が Kaka アプリを編集すれば、Kaka のルールは無視される。テスト用のワークスペースでは、あるプロジェクト独自の deny ルールが、そのプロジェクトのワーカーを確認なしで止めた。ルート側のセッションには、そのルールはまったく効かなかったはずだ。

だから各プロジェクトに専用のワーカーを置く。プロジェクトごとに 1 つ、タスクはキューに並び、再起動をまたいでセッションを再開する。頭脳はすぐに「やっておく」と答え、ワーカーはバックグラウンドで動き、終わると彼女が自分から結果を報告する。

頭脳を読み取り専用に保つのに必要だったのは、コードではなく設定だった。

```python
MAIN_CANNOT = ["Edit", "Write", "NotebookEdit"]
MAIN_SANDBOX = {"enabled": True, "allowUnsandboxedCommands": False}
# plus deny rules passed through settings, e.g. Edit(//<workspace>/**) and Read(**/.env)
```

最初は自前でシェルコマンドのガードを書いた。ところがプローブしてみると、Claude Code のサンドボックスのほうがうまくやる。`cat alpha/.env` は、コマンドの書き方に関係なく OS から「Operation not permitted」で失敗する。ガードのパーサーは不要になった。その後、Claude Code がすでに持っている機能を全部見直して、Python が約 770 行減った。

## 確認はキー入力で、言葉ではない

ワーカーは自分のターミナルと同じく、Claude Code の **auto モード**で動く。以前は、Kaka のタスクひとつで無害なシェルの読み取りが 5 回続けて画面の承認待ちになり、アシスタントとして煩わしかった。auto モードでは、Claude Code 自身の分類器が安全な操作を承認し、危険な操作を止める。

それでも Claude Code が確認したいものは、SDK の `can_use_tool` コールバックで届く。Saturday はそれをパネルとして表示する。平易な見出し、どの依頼のための操作か、その下に diff かコマンド。答えは `y`（許可）、`a`（常に許可）、`n`（拒否）のキーで返す。

**「はい」と言っても通らない。** 音声認識は優秀だが完璧ではなく、`git push` の前で聞き間違えた「はい」は割に合わない。確認内容について声で質問すると、彼女が説明して、どのキーを押せばいいか教えてくれる。

## 会話できる速さにする

最初のエンドツーエンドの実行では、質問から答えまで **21.6 秒**かかった。大半は質問ごとの新しい `query()` だ。新しい Claude Code プロセス、約 27k トークンのシステムプロンプト、それからいくつかのファイル読み込み。起動時にウォームアップした長寿命の `ClaudeSDKClient` ひとつに切り替えると、同じ種類の質問が **5.5 秒**まで縮んだ。

次に、repo についての日常的な質問 6 つでフロントのモデルを選んだ。各モデルをそれぞれ専用のウォームなセッションで、low effort で動かした。

| モデル | 正解 | 時間（中央値） | 答えの長さ（中央値） |
| --- | --- | --- | --- |
| Haiku | 6/6 | 4.2 s | 61 文字 |
| Sonnet | 6/6 | 2.7 s、再実行で 2.1 s | 39、再実行で 34 文字 |
| Opus | 6/6 | 2.1 s、再実行で 5.2 s | 28、再実行で 33 文字 |

Haiku が Sonnet より遅かったのは、ツール呼び出しが一番多く、一番よくしゃべったからだ。Opus は 1 回目に勝って再実行で負けた。Sonnet は 2 回とも速かったので答える役を担い、Opus はバックグラウンドで重い仕事をする。

速さと同じくらい、短さも大事だ。プロンプトは結論を一文だけ求める。コード、パス、箇条書き、markdown は禁止、質問の繰り返しも、何を確認したかの実況もなし。答えは 3〜4 文から、中央値で約 35 文字になった。コードと diff は画面に出すものだ。

今では、話し終えてから彼女の最初の一言まで、Claude がどれだけ読むかによって 4〜6 秒。その大部分は Claude 自身の時間だ。

## 壊れたもの

**自分の声を聞いていた。** MacBook のスピーカーで鳴らすと、彼女の声は部屋の雑音より 14〜16 dB 大きくマイクに届き、自分の発話として文字起こしされるほどだった。解決策は、FaceTime と同じエコーキャンセラーである macOS の voice processing を、`AVAudioEngine` を動かす小さな Swift ヘルパー経由で使うこと。適応に彼女の発話が約 1.5 秒必要で、その後 30〜43 dB 打ち消す。なのでヘルパーはセッション中ずっと動かし、再生も同じエンジンを通し、適応するまではマイクをゲートする。途中の驚きが 2 つ。出力ノードに触る前に有効にするとエラー `-10875` で失敗し、マイクが急に 9 チャンネルを報告するようになった。

**何でも割り込みになった。** 以前は咳や「うんうん」で、彼女が文の途中で止まっていた。今は、彼女が話している間は「Saturday」で始まる発話だけが割り込める。それ以外はローカルで保留され、文字起こしにも送られない。

**間で質問が分割された。** 文の終わりと判断する間は最初 0.8 秒で、0.6 秒まで下げたところ、考えるために言葉を止めるたびに質問が半分に切れた。今は 1 秒だ。さらに、彼女が最初の一言を発するまでに自分が言ったことは、すべてひとつのターンとして扱う。断片はマージされ、質問の半分に対する答えは捨てられる。

**答えがひとつずつズレた。** 答えが 1 秒で切れ、次の答えが前の答えの尻尾から始まった。アーカイブを見ると一目瞭然だった。218 文字に 0.9 秒の音声、次の 109 文字に 16.35 秒。読み上げはすべて 1 本の WebSocket を共有していて、本当の答えがつなぎを途中で切ったとき、つなぎを自分の側だけでキャンセルしていた。サーバーはそれを次の読み上げに流し続けた。今は `response.create` ごとにタグを付け、自分の `response_id` のイベントだけを受け取り、切った読み上げはサーバー側でもキャンセルする。同じ 108 文字の文が、2.2 秒の音声から 8.4 秒になった。

**AirPods で音声が黙って壊れた。** デバイスが変わると `AVAudioEngine` はエラーも出さずに止まる。ヘルパーを再起動すると悪化した。voice processing エンジンをひとつ起動すると他のエンジンが止まるので、新しいプロセスがループした。今はヘルパーがその場でオーディオグラフを組み直し、Saturday は Mac の出力デバイスを毎秒確認する。AirPods のときは普通の音声を使う。voice processing を使うと、低音質の通話モードに固定されてしまうからだ。スピーカーに戻るとエコーキャンセルを再びオンにする。

## 次にやること

ロードマップから：

- **リモートサーバー。** 学習ジョブ、GPU、ログについて聞けるようにする。Mac から Claude が SSH でコマンドを実行するか、頭脳をサーバーに移して音声だけローカルに残すか。イベントストリームはすでに JSON 行なので、後者はほぼトンネルを張るだけだ。
- **表示用スクリーン。** diff、表、グラフは画面に出し、何かを読み上げるかわりに「左の 2 番目のファイルを見て」と言う。
- **残っているチェック。** タスクが自分を必要としたときの Mac 通知、音声レイヤーが勝手に答えたり話を盛ったりしないかを確かめる 20 問の評価、そして 20 分の連続稼働テスト。

git の履歴は 11 月 3 日の深夜から翌日の午後まで、79 コミット。一番効いた判断は削除だった。全二重の音声モデル、手書きのガード、そして Claude Code 自身のバックグラウンドタスク（バックグラウンドの仕組みはワーカーだけにした）。残ったものは意図して小さい。2 つの耳と 1 つの口、すべてを読むひとつの会話、そして各プロジェクトの中でそのプロジェクトのルールに従うワーカー。
